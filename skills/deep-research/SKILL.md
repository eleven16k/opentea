# Deep Research — 研究 → 对抗辩论 → 整合

四个阶段顺序执行，不合并。核心信念：**方案的质量来自对抗，不来自共识表演**。

```
阶段0 立项 → 阶段1 研究（并行） → 阶段2 三角色辩论（2-3轮） → 阶段3 整合
```

工作目录：`docs/research/<主题>/`（用户指定了就用用户的），符合 context-builder 的三层约定。过程文件全部落盘——辩论纪要和被证伪的选项和最终方案同样重要。

## 阶段 0：立项

与用户确认四件事，缺一就问，不要自作主张：

1. **研究问题** — 一句话，可判定做没做成
2. **成功标准** — 最终方案要回答什么、给谁看、什么粒度
3. **范围与禁区** — 必须覆盖的角度；不许碰的约束（时间/预算/技术栈/合规）
4. **研究员分工** — 默认 3 名：市场与竞品、技术可行性、用户证据；按问题调整，2-5 名之间

立项完成即建目录，进入阶段 1，之后**不再回来问用户**——中途的分歧留给辩论，辩论解决不了的留给最终交付的"决策点"章节。

## 阶段 1：研究（并行派遣）

每名研究员一个独立的子 agent，**同一批发起，并行执行**。每人的提示词包含：

- 研究问题、成功标准、范围与禁区
- 自己负责的角度（详细展开）+ 其他研究员的角度（避免撞车，鼓励交叉引用）
- 可用的采集手段（浏览器、WebSearch、仓库检索）与时间预算
- 产出要求：写入 `reference/`（原始材料）并产出报告 `context/研究-<角度>.md`

研究员报告固定结构：

```markdown
# 研究：<角度>
## 结论（≤5 条，每条标注置信度 高/中/低）
## 证据（每条结论 → 出处 URL / reference/ 文件）
## 反面证据（主动去找的；真没找到就写"未发现"）
## 开放问题（我答不了的，及为什么）
```

**禁止**：研究员互相通信；研究员下结论代替辩论；无出处的结论（写明置信度为低也比编造强）。

全员完成后，主控汇总成**证据包** `evidence.md`：
- 合并全部结论，按主题归类
- **标出矛盾点**（来源间或研究员间的冲突）——逐条列出，不做裁决
- **标出证据缺口**（开放问题里反复出现的）
- 矛盾点和缺口是辩论阶段的主战场，必须显式列出

## 阶段 2：对抗辩论（三角色，2-3 轮）

三个角色各派一个子 agent，都读同一份证据包 + 此前全部辩论纪要：

| 角色 | 守护的东西 | 攻击手法 |
|---|---|---|
| **研究员** | 证据质量 | 无出处的结论、虚高的置信度、缺失的反面证据、"我觉得"式论断 |
| **系统架构师** | 可行性 | 技术假设、集成成本、维护性、被忽略的约束、过度设计 |
| **产品经理** | 价值 | 范围蔓延、优先级错置、用户价值无证据、"这是手段不是目的" |

每轮规则：

1. 每角色输出两部分：**本方立场**（≤3 条）+ **对另外两方的反驳**（每方至少一处，必须引用对方原话再驳）
2. **必须攻击**：某轮找不出有效反驳 = 证据包太弱，整条流水线退回阶段 1 补研究
3. 可以改立场，但必须写明"被什么证据/论证说服"——被说服不是失败，无声妥协才是
4. 三方发言**并行发出**（互不可见），由主控收齐后统一写入纪要 `debate.md`（按轮分节，保留原话），下一轮全员可见

轮数：
- 默认 2 轮
- 第 2 轮结束后若剩 2 个以上未决分歧，加第 3 轮
- 3 轮后仍未决的分歧 = **显式分歧**，原样带进整合，不强行统一

## 阶段 3：整合

由**主控**完成（不派子 agent，不充当任何角色），产出 `proposal.md`：

```markdown
# 方案：<主题>

## 最终方案
（三方都接受的部分，直接写结论，不再复述辩论）

## 显式分歧 → 决策点
（谁主张什么、依据是什么、卡在什么证据上 → 需要用户拍板的，给出选项和各自代价）

## 被证伪的选项
（辩死了的方案和死因——防止三个月后翻旧账重来）

## 证据地图
（结论 → 出处，继承研究员报告的引用链）

## 下一步
（可执行动作清单；若存在 docs/agents/issue-tracker.md 则按其约定建票，没有就停）
```

向用户呈现的顺序：**先方案 → 再分歧决策点 → 最后证据地图**。显式分歧是交付物的一部分，不是缺陷——它告诉用户钱该花在哪次决策上。

## 与其他技能的衔接

- 研究阶段的采集与归档遵循 **context-builder** 的三层约定；已有的 `context/` 共享知识直接复用
- 立项前若想法未经需求验证，建议先跑 **office-hours**；PAUSE 的东西不值得进流水线
- 整合产出的决策点被用户拍板后，由下游技能（to-spec / to-tickets 类）接手

## 可选：多模型外部顾问

默认三角色由当前 agent 的子 agent 机制承担。若希望引入**模型多样性**（不同模型真的会以不同方式出错和反驳），在项目放一个 `docs/agents/counsel.md`，把角色映射到本机已装 CLI 的非交互命令，例如：

```markdown
# 外部顾问映射
研究员: codex exec --sandbox read-only "<角色提示词> <待反驳材料>"
架构师: <zcode 或 qoder 的非交互命令，用户自行填写>
```

规则：
- 有该文件：对应角色的子 agent 在形成本方立场前，先带着角色提示词咨询外部 CLI，把回答并入本方论点并**标注来源**（如"外部顾问（codex）指出…"）
- 没有该文件：纯内部辩论，**不主动调用**任何外部 CLI
- 外部顾问的回答同样接受其他角色的反驳——顾问不豁免
