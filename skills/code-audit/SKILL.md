# Code Audit — 分层代码审核

改编自 `@alibaba-group/open-code-review` 的 Delegation Mode，但适配 opentea 的 AC 判定与证据链要求。

**核心分工**：工具做确定性的"找该看哪里"，agent 做需要判断的"这行有没有问题"。两者不混——工具不猜，agent 不找。

## 为什么分层

一次全仓审核有两个硬约束：
1. **上下文装不下** — 大仓几千文件，无法全部读入单个 agent 的窗口
2. **注意力被稀释** — 漫无目的地读代码，检出率远低于目标驱动

分层解决这两点：先用图谱和规则把范围收窄到可疑处，再把有限注意力集中在真正的判断上。

## 阶段 0：确定审核范围与契约

先问清楚（或从任务推断）：

| 项 | 说明 |
|---|---|
| **范围** | 增量（一个 PR / diff）还是全仓？增量时锁定 base..head 的 commit 范围 |
| **AC 清单** | 冻结的验收条件。没有 AC 的审核只能给建议，不能给 PASS |
| **制品版本** | 精确的 commit / tag。**不接受"工作区现在的样子"** |
| **重点维度** | 安全 / 正确性 / 领域边界 / 可维护性 / 性能（默认全要，用户可收窄）|

读审核对象时，**只读已提交的制品**。不读未提交的工作区状态——那是另一个人的现场，不是审核对象。

## 阶段 1：确定性筛选（不调LLM，不消耗模型额度）

按优先级依次执行，前一步的结果收敛后一步的输入：

### 1.1 图谱定位（若有 codegraph 索引）

先在图上定位，再读源码。图是定位依据，**当前源码和测试才是行为证据**。

```bash
codegraph explore "<改动涉及的符号>"    # 找定义、调用者、被调用者、受影响测试
```

标注**盲区**：图不支持的语言、动态导入/反射路径。

### 1.2 改动面收敛

```bash
git diff --stat <base>..<head>              # 改动规模
git diff <base>..<head> -- <关键路径>       # 具体改动
git ls-files <path>                        # 确认真实被git 跟踪（防扫到未入库文件）
```

**增量审核时，只审改动触及的文件及其直接影响面**。未触及的历史代码不在本次范围——但若发现改动**依赖**的历史代码有隐患，记为观察项而非阻断项。

### 1.3 规则扫描（可选）

用 grep/rg 做高信噪比的机械筛查，命中的再送人工判断：

| 维度 | 筛查什么 |
|---|---|
| 鉴权 | 免鉴权注解、`@PermitAll`、缺归属校验的入口方法 |
| 凭据 | 硬编码密钥、`SECRET`/`TOKEN`/`PASSWORD` 字面量、`.env` 是否被 git 跟踪 |
| 前端信任 | 前端直连外部服务（LLM/支付/地图）的客户端 key |
| 迁移遗留 | 已废弃 API、框架迁移未收尾的调用 |

**扫描结果不是结论**，是候选。命中不等于有问题，不命中不等于没问题。

### 1.4 产出候选清单

输出一份清单：文件 + 行号 + 命中规则 + 为什么可疑。**这一步不写任何判断结论。**

## 阶段 2：分批并行审核（agent 判断）

### 2.1 分批原则

- 每批 **5-15 个文件**，按模块或主题聚在一起，不要把不相关的文件凑一批
- 每批独立并行，批次之间不共享上下文
- 优先审安全相关的文件——它们的问题后果最不可逆

### 2.2 每批的审核输入

审核者拿到：
- 该批的文件清单 + 具体行范围
- 相关的 AC（若有）
- **判定标准**（见下）

### 2.3 判定标准：证据必须可复核

每条发现必须给：
- **文件:行号**（精确，不是"这个文件里有..."）
- **失败场景**（什么输入 / 什么状态 → 什么错误结果）
- **为什么这是问题**（后果是什么，不只是违反了哪条风格）

判定为阻断级（CHANGES_REQUESTED）需要三者齐全。缺失败场景的，降级为建议。

### 2.4 区分系统性问题与散点bug

**这是本skill 最重要的判断。**

| | 系统性问题 | 散点 bug |
|---|---|---|
| 特征 | 多处同根因、缺的是架构约束 | 单点逻辑错误 |
| 修法 | 加统一约束（切面/中间件/校验层） | 改这一行 |
| 报告方式 | 单列一节，说明影响面和根治方案 | 逐条列 |

一个典型的系统性判断：*"后端 28 处接口缺归属校验，根因是 App 层没有统一的归属校验切面——建议加 `requireOwnedResource(id)` 切面并补一条集成测试断言跨用户访问必被拒"*

这比列 28 条 "X接口缺校验" 有用得多——**前者告诉团队改哪里能一劳永逸，后者只是噪音。**

## 阶段 3：复核（防止转述失真）

**子批次审核者的结论是待验证的草稿，不是终稿。**

主控必须对每一条 critical/high 亲自复核：
- 读实际代码，确认行号和描述属实
- 确认文件真的被 git 跟踪（`git ls-files`）
- 确认失败场景真实可达，不是理论上的

复核不通过的直接删除，**不要为了报告好看而保留可疑结论**。

这一条不可省——批量审核最容易出现的问题是子审核者的幻觉，而 hallucination 在报告里看起来和真实发现一模一样。

## 阶段 4：AC 判定与报告

如果这次审核有冻结 AC（增量审核通常有），逐条判定：

| AC | 实际结果 | 判定 | 证据 |
|---|---|---|---|
| AC-01 | 可观察行为 | MET / NOT_MET / **UNPROVEN** | E1 |

**`UNPROVEN` 是独立状态**：证据不足既不是通过也不是失败。不许用 NOT_MET 掩盖"没能力验证"，也不许默认 MET。

四种结论：

| 结论 | 条件 | 后续 |
|---|---|---|
| **PASS** | 全部适用 AC 有证据支撑且满足 | 进入约定的发布/验收阶段 |
| **CHANGES_REQUESTED** | 证据证明某 AC 未满足 | 退回，列阻断项 + 对应 AC + 预期行为 |
| **NEEDS_EVIDENCE** | 证据不足 | 补证后再审，**不假称代码错误** |
| **ESCALATE** | 涉及需求/架构争议，超出审核权限 | 交 PM 裁定 |

### 报告写Plane workitem comment

完整报告进 Plane，短通知 ≤300 字符只做定位。报告里**开发完成 / 审核通过 / 已部署 / 业务验收分别陈述**，禁止统称"完成"。

## 增量审核 vs 全仓审计

| | 增量（每张票） | 全仓（一次性） |
|---|---|---|
| 范围 | base..head + 直接影响面 | 全部纳入文件 |
| AC | 通常有，逐条判定 | 无，只能给建议 |
| 分批 | 通常 1-3 批 | 可能 20+ 批，需并行调度 |
| 结论 | PASS/退回/补证 | 问题清单 + 处理顺序建议 |
| 频次 | 每张票 | 定期（如每月/大版本前） |

**每张票都做全仓审计是反模式**——重复劳动且稀释注意力。

## 纪律

1. **不用工具输出代替判断** —— 图谱定位到文件，不等于该文件有问题
2. **不因"扫描没命中"就放行** —— 规则扫描有盲区，高级问题（业务逻辑、口径错误）扫不出来
3. **不把猜测写成结论** —— "这里可能有并发问题"是观察项；"两个线程同时写这个字段，会丢失更新"才是发现
4. **不跳过复核阶段** —— 批量审核的结论必须主控亲自验证
5. **不用 NOT_MET 代替 UNPROVEN** —— 承认自己没验证，比编一个失败结论诚实
